## 4. 단계별 명세

이 문서에서 "단계"는 두 가지로 쓰인다. 3–4절의 1–10단계는 PR 하나가 거치는 **흐름의 단계**이고, 13절의 0–6단계는 **구현 단계**다. 3–4절 밖에서 구현 단계를 가리킬 때는 "구현 ○단계"라고 쓴다.

각 단계는 입력, 출력, 캐시 키, 실패 시 동작을 먼저 적고 세부 규칙을 붙인다. 모든 단계는 시작 전에 자기 커밋이 아직 PR의 최신 커밋인지 확인하고, 아니면 정리하고 끝낸다.

### 4.1 수신: 웹훅 · 동기화 · 큐

| | |
| --- | --- |
| 입력 | GitHub 웹훅, 주기 동기화가 본 PR 상태 |
| 출력 | 큐의 `PRJob` |
| 캐시 키 | 없음. 중복 방지 키는 `(repo, PR 번호, head SHA, 작업 종류)`, 명령은 코멘트 ID |
| 실패 시 | 서명 실패는 401. 그 밖에는 큐에 넣지 않고 다음 동기화가 채운다 |

지금 구현을 그대로 쓴다. 규칙은 v1 F1–F3과 같고 요점만 옮긴다.

- **웹훅 (v1 F1):** `POST /webhook/github` 하나. `X-Hub-Signature-256` HMAC 검증, `X-GitHub-Delivery` ID로 재전송 제거, 허용 목록의 저장소만, 큐에 넣고 바로 202. api는 GitHub을 조회하지 않는다. PR 작성자의 `author_association`과 로그인 이름은 판단 없이 기록용으로 `PRJob`에 실어 넘긴다. 외부 작성자의 PR을 돌릴지는 워커가 GitHub에서 직접 읽은 값으로 정한다(8.6). `issue_comment`는 `created`이고, 파이프라인 자신의 코멘트가 아니고, 작성자의 `author_association`이 OWNER·MEMBER·COLLABORATOR인 것만 받는다. 코멘트를 다루는 이벤트 셋을 더 받는다: `pull_request_review`(submitted)와 `pull_request_review_comment`(created)는 글쓴이가 Copilot이거나 OWNER·MEMBER·COLLABORATOR일 때 `feedback`이 되고, 머지된 수정안 PR(`pipeline/pr-<n>-fix-<묶음>`)의 `pull_request` closed는 원래 PR n의 `resolve`가 된다. `issue_comment`는 명령이 아니면 같은 규칙으로 `feedback`이 될 수 있다. 파이프라인이 단 글(`<!-- pr-proof` 표시)과 `/` 명령은 `feedback`이 되지 않아, 답글이 다시 이벤트를 일으켜 도는 일이 없다. 웹훅·동기화·워커가 `feedback_in_comment()` 하나로 거른다.
- **동기화 (v1 F2):** api 시작 시 한 번, 이후 5분마다. GitHub의 PR 상태와 SQLite의 처리 이력을 비교해 차이를 작업으로 넣는다.

  | 비교 | 차이가 있으면 |
  | --- | --- |
  | 열린 PR의 head SHA와 그 SHA로 끝난 검사 이력 | `update` |
  | 열린 수정안 PR이 남았는데 GitHub에서는 닫힌 원본 PR | `close` |
  | PR 코멘트의 명령과 처리한 코멘트 ID | `command` |
  | 다룰 코멘트(Copilot 리뷰, 사람의 리뷰) 중 처리하지 않은 것 | `feedback` |
  | 수정안 PR의 머지를 기다리는 받아들인 코멘트(해결하지 않은 스레드) | `resolve` |
  | "실행 중"인데 생존 확인이 끊긴 작업 | 다시 등록 |

  | 같은 head의 마지막 `runs` 상태 | 같은 head를 다시 넣나 |
  | --- | --- |
  | `done` | 지금 코드가 낸 결과면 넣지 않는다. 옛 코드가 낸 결과면 넣는다 (아래) |
  | `env_error` (재시도를 모두 씀) | 마지막 시도 뒤 30분이 지났을 때만 |
  | `error` (파이프라인 버그, 작업 시간 초과) | 지금 코드에서 난 오류면 넣지 않는다. 옛 코드에서 난 오류면 넣는다 (아래) |
  | `running`인데 생존 확인이 20분 끊김 | 죽은 워커의 작업 키를 지우고 넣는다 |
  | `cancelled` | 그 head가 다시 최신이고 `done`이 없을 때만 |
  | `blocked` (외부 작성자의 PR이 승인을 기다림, 8.6) | 넣지 않는다. 승인 명령이나 새 커밋이 다시 돌린다 |
  | `elsewhere` (같은 저장소를 보는 다른 서버가 이 커밋을 이미 처리함, 4.9) | 넣지 않는다. 새 커밋 때만 |
  | `deferred` (다른 서버가 이 커밋을 처리하기를 기다림, 4.9) | 마지막 기록 뒤 30분이 지나면 한 번 더 넣는다(`deferred`). 워커가 그 서버가 처리했는지 다시 보고, 처리했으면 `elsewhere`로 끝내고 아니면 넘겨받는다 |
  | 기록 없음 | 넣는다 |

  **옛 코드가 낸 결과는 `/recheck` 없이 다시 검사한다 (2026-11-22, `new_pipeline`).** `runs`의 줄마다 그 검사를 돌린 파이프라인 코드의 커밋(`pipeline_commit`, 프로세스가 뜰 때의 `git rev-parse HEAD`. `app/shared/version.py`)을 남긴다. 같은 head의 끝난 결과(`done`, `error`)가 모두 지금 도는 코드와 다른 커밋의 것이면 동기화가 `update`를 넣는다. 배포하고 서버를 다시 띄우면 첫 동기화가 열린 PR을 모두 한 번씩 다시 검사하고, 지금 코드로 끝난 줄이 생기면 다시 넣지 않는다. 이 열이 생기기 전의 줄(NULL)은 옛 코드의 것으로 본다. 지금 코드의 커밋을 알 수 없으면(git이 없는 배포) 이 규칙을 쓰지 않는다. 다시 검사해도 모델 호출의 저장된 결과는 키(프롬프트 판 포함)가 같으면 그대로 쓰인다(9.1). `blocked`는 코드가 바뀌어도 승인을 기다린다. `elsewhere`와 `deferred`는 끝난 결과로 세지 않는다. 마지막 기록이 `blocked`, `elsewhere`, `deferred`인 PR에는 리뷰 코멘트 작업(`feedback`)도 넣지 않는다.

  서버가 꺼진 동안 커밋이 쌓였어도 최신 head만 검사한다. 놓친 명령은 현재 head의 커미터 시각 뒤에 달린 것만 처리한다(`?since=`로 줄이고 작성 시각으로 한 번 더 거른다). 권한 확인은 웹훅과 같은 함수를 쓴다. 수동 실행은 `python -m app.api.cli sync`이고 HTTP 엔드포인트는 만들지 않는다. 동기화로 처리한 검사는 코멘트에 "동기화로 처리됨 (웹훅 누락)"을 남긴다.
- **큐와 워커 (v1 F3):** Redis + RQ, 동시 작업 1개. 같은 PR에 새 커밋이 오면 최신 커밋만 처리한다. 워커는 노드 사이와 샌드박스 실행 중(10초마다)에 Redis의 최신 head를 확인하고, 낡았으면 컨테이너와 worktree를 정리하고 끝낸다. `update`를 시작할 때 GitHub에서 실제 head를 조회해 Redis 값을 바로잡는다(웹훅 순서가 뒤집힌 경우). 환경 오류는 `env_error`, 그 밖의 예외는 `error`로 남기고 RQ가 재시도한다. 마지막 시도가 실패하면 작업 키를 지운다.
