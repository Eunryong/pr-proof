### 4.9 전달

| | |
| --- | --- |
| 입력 | 규칙 묶음, 위반, 수정 판단, 출구 검사를 통과한 패치와 설명 JSON, 만든 테스트의 기록, 테스트 결과 |
| 출력 | 결과 코멘트(원래 PR), 수정안 PR, 줄 리뷰 코멘트, `proposals` 기록 |
| 캐시 키 | 없음. 중복 방지는 마커와 기록 확인(5.6) |
| 실패 시 | gh·git 실패는 환경 오류로 재시도. 이미 한 것은 건너뛴다 |

**원래 PR의 결과 코멘트 (v1 F9)**

- PR당 코멘트 하나를 달고 진행하면서 같은 코멘트를 고친다. 저장한 코멘트 ID가 404면 마커(`<!-- pr-proof -->`)와 작성자로 다시 찾고, 없으면 새로 단다.
- 맨 위가 결론이다(2026-11-22). 테스트는 글자로만 쓰고, 기호(⚠️/✅)는 규칙 줄과 PR 단위 줄에만 쓴다. ⚠️는 "위반 있음", ✅는 "위반 없음"이라는 뜻으로만 쓴다. 위반이 있으면 건수를, 없으면 읽은 규칙 중 몇 개를 무엇으로 확인했는지를 말한다. PR 단위 위반은 따로 된 줄이 말한다(있을 때만).

  ```
  **테스트:** 통과 (9개)
  **규칙:** ⚠️ 위반 3건 (규칙 2개) · 수정안 #15
  **PR 단위:** ⚠️ 위반 1건 (규칙 1개) · 알리기만 함 (커밋 메시지, PR 글, 브랜치 이름은 수정안으로 고칠 수 없음)
  ```

  ```
  **테스트:** 통과 (6개)
  **규칙:** ✅ 위반 없음 · 규칙 4개를 확인함 (도구·검사기 1개, 모델 판단 1개, 테스트·정적 검사 결과 1개, PR 단위 1개)
  ```

  - 위반 수에는 코드 위반과 모델이 어겼다고 답한 실행 결과의 규칙(4.5)이 들어간다. 수정 판단의 모델이 위반이 아니라고 답한 것(4.6)은 들지 않는다.
  - 확인하지 못한 규칙이 있으면 "규칙 N개 중 M개를 확인함"이고, 하나도 확인하지 못했으면 "확인한 규칙 없음 (읽은 규칙 N개)"이다. "검사하지 않음"이라는 말은 쓰지 않는다.
- 결론 아래는 펼친 부분과 접는 블록 하나("자세히: 규칙별 확인 방법, 모델 호출, 바뀐 줄 커버리지")로 나뉜다. 펼친 부분에는 사람이 할 일이 있는 것만 둔다: 위반, 실행 결과로 어긴 규칙, 수정 판단과 수정 결과, PR 단위 위반, 확인하지 못한 규칙과 그 까닭, 위반을 찾은 검사기의 본문. 위반이 없고 모두 확인했으면 펼친 부분이 없다. 나머지(읽은 규칙과 규칙마다의 확인 방법, 모델이 위반이 아니라고 본 것, 호출 수와 토큰, 테스트 수, 바뀐 줄 커버리지, 검색 기록)는 접는 블록에 넣는다.

- **PR 설명 (4.5 끝 "PR 설명과 diff 견주기", 2026-11-22).** PR 설명 확인을 한 검사는 결론 줄들 끝에 "PR 설명:" 줄 하나가 붙는다(규칙이 없어도). 기호는 쓰지 않는다. 문구는 이대로다.
  - 맞을 때: `**PR 설명:** 설명한 내용과 변경이 맞습니다.` 펼친 부분은 없다.
  - 어긋날 때: `**PR 설명:** 설명과 다른 곳이 N건 있습니다.` 펼친 부분(테스트의 상세 다음, 규칙 절 앞)에 "**PR 설명과 다른 곳:**"과 항목들, 그리고 "PR 제목·본문을 고쳤으면 `/recheck`를 달아 다시 견주세요"를 둔다. 항목은 머리말 「PR과 관련 없는 수정」, 「설명에는 있는데 코드에 없음」, 「설명과 다름」 뒤에 모델이 쓴 한두 문장(코드 스팬 안, 300자까지)과, 바뀐 줄이 있으면 `(파일:줄)`(지운 줄이면 ", 지운 줄")이다. 분류 이름(`unrelated` 등)은 쓰지 않는다. 맞게 된 항목은 나열하지 않는다.

    ```
    - PR과 관련 없는 수정: `config.py에서 기본 타임아웃을 30초에서 5초로 줄였습니다. 설명에는 파서 수정만 적혀 있습니다.` (`config.py:1`)
    - 설명에는 있는데 코드에 없음: `"오류 메시지를 한국어로 바꿨다"고 했지만 바뀐 메시지를 찾지 못했습니다.`
    - 설명과 다름: `재시도를 3회로 한다고 했는데 코드는 5회입니다.` (`client.py:88`)
    ```
  - 설명이 비었을 때: `**PR 설명:** 설명이 비어 있어 견주지 못했습니다.` 펼친 부분에 "PR 본문이나 커밋 메시지에 무엇을 바꿨는지 적고 `/recheck`를 달면 견줍니다."
  - 견주지 못했을 때: `**PR 설명:** 견주지 못했습니다 (모델 호출 상한에 걸림).`(또는 "모델 호출이 실패함", "PR 글을 읽지 못함", "바뀐 내용이 없음"). 펼친 부분에 까닭(코드 스팬)과, 상한·실패면 "다음 커밋의 검사나 `/recheck`가 다시 견줍니다."
  - diff나 PR 글을 상한에서 잘랐으면 펼친 부분에 "변경이 커서 바뀐 파일 N개 중 M개는 diff를 다 보이지 못했습니다…", "PR 글이 길어 앞부분만 견줬습니다."를 적는다.
  - 접는 블록에 "PR 설명 확인: 모델 호출 N회 · 읽기 도구 T회 · 저장된 결과 K건 사용 · 모델 · 버린 답 D건 · 토큰 입력 A, 출력 B"를 둔다.
  - `.pipeline.yaml`로 끈 저장소는 이 줄이 없다.

- **이슈 (4.5 끝 "연결된 이슈 확인", 2026-11-23, pr-proof#75).** 이슈 확인을 한 검사는 "PR 설명:" 줄 아래(PR 설명 확인을 끈 저장소는 결론 줄들 끝)에 "이슈:" 줄 하나가 붙는다(규칙이 없어도). 기호는 쓰지 않는다. 기계적인 분류 이름을 쓰지 않고 리뷰어가 말하듯 적는다. 문구는 이대로다.
  - 해결했을 때: `**이슈:** #73이 요구한 것을 해결했습니다.` 여럿이면 `**이슈:** #73, #75가 요구한 것을 해결했습니다.`(조사는 마지막 번호를 읽은 소리로 고른다) 펼친 부분은 없다.
  - 빠진 것이 있을 때: `**이슈:** #73이 요구한 것 중 빠진 곳이 N건 있습니다.` 펼친 부분(PR 설명 절 다음, 규칙 절 앞)에 항목 `- 이슈가 요구했는데 빠짐: <모델이 쓴 한두 문장(코드 스팬, 300자까지)> (#73)`과 "이슈 글을 고쳤으면 `/recheck`를 달아 다시 견주세요. 이슈만 고친 것은 저절로 다시 보지 않습니다."를 둔다. 항목마다 어느 이슈인지 붙인다.
  - 코드로 확인할 수 없는 요구: 펼친 부분에 `- 코드로 확인할 수 없음: <무엇> (#73)`. 결론 줄의 건수에는 넣지 않는다(이것만 있으면 결론 줄은 "해결했습니다"다).
  - 연결된 이슈가 없을 때: `**이슈:** 연결된 이슈가 없습니다.` 경고 표시를 붙이지 않고 모델을 부르지 않는다.
  - 견주지 못했을 때: `**이슈:** 견주지 못했습니다 (모델 호출 상한에 걸림).`(또는 "모델 호출이 실패함", "이슈를 읽지 못함", "다른 저장소의 이슈만 연결됨", "바뀐 내용이 없음"). 펼친 부분에 까닭(코드 스팬)과, 상한·실패면 "다음 커밋의 검사나 `/recheck`가 다시 견줍니다."
  - 보지 않은 것: 다른 저장소의 이슈는 ``- 다른 저장소의 이슈라 보지 않음: `owner/name#N` ``(이름은 코드 스팬)으로, 상한을 넘은 이슈는 "연결된 이슈가 많아 앞의 5개만 견줬습니다", 읽지 못한 이슈, 잘린 diff, "이슈 글이나 댓글이 길어 일부만 견줬습니다."를 펼친 부분에 적는다.
  - 접는 블록에 "이슈 확인: 모델 호출 N회 · 읽기 도구 T회 · 저장된 결과 K건 사용 · 모델 · 버린 답 D건 · 토큰 입력 A, 출력 B"(PR 설명 확인의 줄과 같은 꼴)와, 있으면 "저장소 사람이 아닌 댓글 N개는 읽지 않음"을 둔다.
  - `.pipeline.yaml`의 `linked_issues.enabled: false`로 끈 저장소는 이 줄이 없다.

- 그 아래에 넣는 것:
  - 위반 목록. **규칙별로 묶는다 (11.2 D6):** 규칙마다 규칙 id와 원문 한 줄, 건수, **출처(문서와 절)**, **쓴 확인 방법**(도구 이름과 코드, 검사기 id, 또는 "모델 판단"과 그 이유)을 적고, 그 규칙의 위반이 같은 메시지(검사기·도구의 메시지, 모델 판단의 까닭)를 가지면 "무엇이 문제인가: `메시지`" 한 줄을 더하고(코드 스팬, 300자까지. 위치마다 메시지가 보이는 도구 설정의 규칙, 메시지가 다르거나 없는 것, 규칙 원문과 공백·대소문자·마침표만 다른 것은 싣지 않는다, 2026-11-23, pr-proof#78), 그 아래에 위반의 파일·줄을 앞 10건만 보인다. 나머지는 규칙마다 접힌 블록에 넣는다(접은 목록의 합은 300건까지, 넘는 것은 건수만). 어느 규칙이든 10건을 넘으면 목록 위에 "규칙이 문서에 새로 추가돼 기존 코드의 위반이 한꺼번에 나온 것일 수 있다"는 안내를 붙인다.
  - 수정안은 크기 상한(4.8의 7번: 바뀐 파일 20개, 바뀐 줄 500줄) 안에서만 만든다. 상한 때문에 수정안에 넣지 못한 위반은 "수정안 크기 상한으로 처리하지 못함: N건"으로 알린다 (11.2 D6).
  - **모델이 만든 검사기의 본문**을 접힌 블록(`<details>`)으로. 이번 검사에서 위반을 찾은 검사기만 넣고, 본문보다 긴 코드 울타리로 감싼다.
  - 수정 판단의 줄: "수정 판단: 고칠 대상 N건, 직접 고쳐야 함 M건". 이유가 여럿이면 "(이유별 건수)"를 붙인다. 규칙마다 고칠 대상은 위치마다 수정 방법과 수정안 PR 번호(이번 검사가 열었거나 갱신했으면)를 적는다. 고치지 않은 위반은 규칙마다 수정안을 만들지 않은 까닭을 문장으로 한 번 적고 그 아래에 위치를 접는다(2026-11-23, pr-proof#78). 이유가 하나면 "직접 고쳐야 함 M건 · 문장" 한 줄이고, 여럿이면 "직접 고쳐야 함 M건" 아래에 "- K건: 문장"을 이유마다 한 줄씩 두고 위치마다 짧은 이름을 붙인다. 위치 줄에는 위치마다 다른 것만 붙인다: 모델이 쓴 이유 글, 거절된 수정안의 번호. 문장은 `doc_rules_report._LEFT_REASON`에 있고, 수정 판단의 이유(4.6)를 뜻을 바꾸지 않고 푼 것이다. 알리기만 하는 규칙은 셋으로 나눈다: 파일 단위 위반("파일 이름이나 위치를 바꿔야 하는 위반이라 수정안을 만들지 않았습니다."), 도구 설정의 규칙 중 도구의 자동 수정이 없는 위반, 규칙의 수정 방법이 `none`인 규칙(4.4 "수정 방법": 다른 파일의 사용처까지 바꿔야 하거나 코드로 고칠 수 없음). "알리기만 하는 규칙"이라는 말은 쓰지 않는다. 코멘트에는 `skip`이라는 말을 쓰지 않는다(2026-11-21). 모델의 이유 글은 코드 스팬 안에만 넣는다.

    ```
    - `R-readme-9b6db85d` `New files and contracts are written in TypeScript or .d.ts (S1).` · 12건
      출처: `README.md > Tech stack` · 모델이 쓴 검사기 (path-pattern)
      무엇이 문제인가: `New files and contracts must be written in TypeScript or .d.ts, not JavaScript.`
      직접 고쳐야 함 12건 · 파일 이름이나 위치를 바꿔야 하는 위반이라 수정안을 만들지 않았습니다.
    ▸ 직접 고쳐야 함 12건의 위치
    ```
  - 테스트가 돌지 않았을 때(위반이 있을 때만). 맨 위 "테스트:" 줄은 짧게 두고 그 아래 펼친 부분에 까닭을 적는다(2026-11-23, pr-proof#78). 테스트가 없으면(pytest가 하나도 찾지 못함) "pytest가 테스트를 하나도 찾지 못해 고친 것을 확인할 수 없으므로 모델 수정안을 만들지 않습니다. 지금 테스트를 돌릴 수 있는 것은 Python(pytest) 테스트뿐입니다."(기계적 수정은 테스트 없이도 한다, 4.6), 시간 초과는 "테스트가 시간 안에 끝나지 않아…", 실행 불가는 "테스트 결과를 얻지 못해 고친 것을 확인할 수 없으므로 수정안을 만들지 않습니다.", 의존성 설치 실패는 "의존성을 설치하지 못해 테스트를 돌리지 못했으므로 고칠지 판단하지 않았고 수정안도 만들지 않았습니다." 위반이 없으면 붙이지 않는다.
  - 수정 결과(수정안 PR 번호 또는 만들지 못한 이유)와 그 아래 "테스트:" 묶음. 고친 위반의 표시는 셋이다: "있던 테스트가 실행함", "만든 테스트가 실행함", "있던 테스트도 만든 테스트도 이 줄을 실행하지 않음"(커버리지를 읽지 못했으면 "테스트가 이 줄을 실행하는지 알 수 없음"). 같은 글이 위반 줄마다 되풀이되지 않게 상태마다 한 줄로 쓰고 그 안에 파일과 줄 번호를 모은다(예: "- 만든 테스트가 실행함 (3건): `a.py` 줄 2, 5 · `b.py` 줄 3"). 어느 테스트도 실행하지 않는 줄은 모델이 적은 까닭을 코드 스팬 안에 붙인다. 이어서 만든 테스트 수와 그 테스트가 실행한 대상 위반 수, 뺀 테스트와 이유(4.8의 6번). 2026-11-22에 "이 줄을 실행하는 테스트가 없음"을 지웠다(테스트 자체가 없다고 읽혔다, 11.1).
  - 호출 상한에 걸렸으면 처리하지 못한 건수: "모델 호출 상한에 걸려 처리하지 못함: 위반 판단 N개 규칙, 수정 M건. `/fix`로 다시 돌릴 수 있습니다"(9.2).
  - 실행 결과로 어긴 규칙(4.5): "테스트·정적 검사 결과로 어긴 규칙 (줄이 아니라 PR에 걸려 수정안은 만들지 않음)" 아래에 규칙, 모델의 까닭, 모델이 본 자료의 요약("근거:").
  - 확인하지 못한 규칙과 그 까닭(펼침): 모델이 판단하지 못함, 호출 상한, 검사기 실패, 체크포인트에 남은 옛 `human` 결과(4.3).
  - 접는 블록: 도구가 잡았지만 모델이 위반이 아니라고 판단한 것의 위치와 까닭, 읽은 규칙과 규칙마다의 확인 방법(실행 결과의 규칙은 모델의 답과 근거), 테스트 수, 바뀐 줄 커버리지. 커버리지 줄은 "바뀐 줄 커버리지 N% (참고, 위반이 아님): 있던 테스트가 PR이 바꾼 줄 M줄 중 K줄을 실행함"이다. 실행하지 않은 줄 수를 앞세우면 문제처럼 읽혀 실행한 줄 수로 쓴다(2026-11-22, 11.1).
  - 검색으로 참고한 과거 기록과 유사도를 접힌 블록으로(6.6). 검색을 켠 저장소만. 검색 상태 줄(6.7)은 켜져 있을 때와, `auto`가 채택률이 낮아 다시 껐거나 켜야 하는데 선택 의존성이 없을 때만 싣는다. 설정으로 끈 것과 기록이 적어 꺼진 것은 싣지 않는다(2026-11-23, pr-proof#78).
  - 이번 검사의 모델 호출 수와 토큰 수(9.4). 수정 작성은 도구 호출 수(규칙 검사, 테스트)와 도구 시간, 상한에 닿았는지를 같은 줄에 더한다.
  - 2026-11-22에 맨 아래의 안내 한 줄(규칙 해석이 틀렸으면 팀의 문서를 고치라는 글)을 지웠다. 도구가 규칙을 잘못 읽었으면 도구가 틀린 것이다(4.3, 11.1).
- 환경 오류일 때는 결과를 쓰지 않고 "환경 문제로 대기 중"만 보인다. 실패처럼 보이는 표시를 남기지 않는다. 테스트가 실패해도 규칙 줄은 보여 준다.
- 명령에 대한 답은 결과 코멘트와 따로 새 코멘트로 달고 `<!-- pr-proof:reply -->`를 붙인다. 모르는 `/` 명령에는 답하지 않는다.

**수정안 PR (v1 F10)**

- 브랜치는 `pipeline/pr-<n>-fix-<mechanical|model>`, base는 원래 PR의 브랜치다. 같은 브랜치의 열린 수정안이 있으면 강제 푸시하고 제목·본문을 고친다.
- 커밋은 허용된 경로만 지정해 스테이징한다(`git add -A`를 쓰지 않는다). 작성자는 로그인한 계정의 noreply 주소, 사용자 전역의 서명·훅은 끈다. 커밋 메시지에는 모델의 글을 넣지 않는다.
- **본문:** 요약(설명 JSON의 `summary`), 해소한 위반과 규칙의 출처(규칙마다 파일과 줄 번호를 묶음), 파이프라인이 쓴 검증 절(허용 범위, 규칙 재검사, 있던 테스트와 만든 테스트의 결과, 크기), "테스트" 절(결과 코멘트와 같은 표시 셋의 묶음, 만든 테스트, 뺀 테스트와 이유), 쓴 모델, "모델이 쓴 코드이니 리뷰한 뒤 머지". 만든 테스트 파일은 수정안 PR에 같이 들어간다. 모델의 글은 그 글보다 긴 코드 울타리 안에 넣는다(멘션·마크업이 동작하지 않게).
- **줄 리뷰 코멘트:** 검증이 채운 `changes`를 (파일, 규칙)으로 묶어, 그 규칙으로 고친 첫 줄에 "규칙, 이유"를 리뷰 코멘트 하나로 단다. 같은 규칙으로 고친 그 파일의 다른 줄은 그 코멘트에 줄 번호로 적는다(30개까지, 넘으면 "외 N곳"). 줄은 파이프라인이 대상 위반의 줄을 바꾼 덩어리에서 정하고, 이유는 모델이 그 (파일, 규칙)에 쓴 글이다. 고친 곳마다 달지 않는 까닭: 이유가 (파일, 규칙)에 하나라 같은 글이 되풀이되고, 첫 큰 수정안(MathLLM#6, 2026-11-21)에서 코멘트가 100개 넘는 리뷰 하나가 GitHub의 2차 한도에 걸려 전달이 실패했다. GitHub이 줄을 받지 않거나(422) 2차 한도로 막으면 리뷰 없이 수정안 PR만 남기고 전달을 이어 간다. 본문의 "모델의 설명"도 같은 (파일, 규칙, 이유)를 한 줄로 묶고 고친 줄 번호를 뒤에 적는다. 보조 변경(import, 새 상수)과, 위반 줄을 그대로 두고 줄을 더하기만 한 수정에는 줄 코멘트가 없다. 리뷰 하나로 한 번에 올린다.
- 포크에서 온 PR은 base가 될 브랜치가 원본 저장소에 없으므로 수정안 PR을 열지 않고, 결과 코멘트에 수정 내용만 보인다.
- 머지 여부는 커밋 메시지가 아니라 저장한 수정안 PR 번호로 GitHub에서 확인한다(`gh pr view --json state,mergeCommit`).

**수정안 PR 상태 관리**

| 상황 | 처리 |
| --- | --- |
| 원래 PR에 새 커밋 | 이전 커밋의 열린 수정안을 닫고 브랜치를 지운다(`superseded`). 새 커밋의 검사가 다시 만든다 |
| 수정안 PR 머지로 생긴 커밋 | head가 그 머지 커밋이고 내용이 검증한 수정안과 같으면 검사하지 않고 검증한 결과를 옮겨 적는다(아래). 같지 않으면 검사만 다시 하고, 같은 묶음의 수정안은 다시 만들지 않는다(루프 방지). 그 뒤의 커밋은 자동 경로를 다시 탄다 |
| 원래 PR 머지·닫힘 | 진행 중인 검사를 멈추고 남은 수정안을 닫고 브랜치를 지운다(`closed_with_pr`). 검사를 멈추는 것은 닫힘 소식을 받은 api다: 받는 즉시 최신 head를 닫힘 표시로 바꾸고(`app/api/queue.py`), 돌던 검사가 다음 확인(단계 사이, 테스트 중에는 10초마다, 모델 호출은 그 호출이 끝난 뒤)에서 멈춰 `cancelled`로 끝난다. 워커는 하나라 닫힘 작업은 돌던 검사가 끝난 뒤에야 돌기 때문에 그 작업이 표시하면 늦다(2026-11-23). 수정안을 닫는 것은 닫힘 작업이 하고, 먼저 GitHub에서 정말 닫혔는지 확인한다. 열려 있으면(닫힘 소식이 다시 열림보다 늦게 옴) 표시를 GitHub의 지금 head로 되돌린다. 동기화가 넣은 닫힘 작업은 api가 표시하지 않는다 |
| 사람이 수정안 PR을 닫음 | `rejected`. 같은 커밋에 다시 올리지 않는다. 그 수정안이 고친 위반의 (파일, 규칙, 앞뒤 공백을 뺀 줄 내용)을 기억해, 다음 커밋에서 같은 것이면 `skip`한다. 줄을 고치면 내용이 달라져 다시 대상이 된다. 파이프라인이 닫은 것(`superseded`, `closed_with_pr`)은 거절이 아니다 |
| 같은 커밋에 열린 수정안이 있음 | 다시 만들지 않고 결과 코멘트에 그 번호를 적는다 |

**수정안의 머지 커밋: 검증한 결과를 옮겨 적기**

원래 PR의 head가 규칙 수정안(`mechanical`, `model`)의 머지 커밋이고 아래 조건이 모두 맞으면, 규칙 읽기, 위반 찾기, 모델 판단, 테스트, 수정을 하지 않고 수정안을 검증한 커밋(V)의 검사 결과와 수정안 검증의 결과를 옮겨 적는다. 판정은 `app/worker/merged_fix_pure.py`, 재료 모으기는 `update.carry_plan`, 옮겨 적기는 `graph.carry_flow`다.

- 내용이 같다: 머지 커밋의 부모에 V가 있고(GitHub의 머지 커밋, 스쿼시, 리베이스 모두), 머지 커밋의 트리가 "V + 저장한 패치(`fix_attempts.patch`)"의 트리와 같다. 트리는 bare 캐시에서 임시 인덱스에 V를 읽고 패치를 `git apply --cached`로 얹어 만든다(worktree 없음). 수정안이 바꾼 파일의 해시만 보지 않는다: V 뒤에 원래 브랜치에 커밋이 더 올라온 뒤 머지했거나 머지에 다른 변경이 섞이면 다른 파일이 달라진다.
- 기록이 있다: 수정안의 시도가 검증을 통과한 패치를 저장했고 그 수정안의 것이다. V의 체크포인트가 코멘트까지 끝났고 멈춘 node가 없으며, 그 수정 결과가 수정안의 시도와 같다. base가 V를 검사할 때와 같다.
- 남은 일이 없다: V에 다른 묶음으로 고칠 위반이나 다른 묶음의 수정안이 없다. 호출 상한으로 남은 모델 판단·수정 판단·PR 단위 판단이 없다.
- 이슈 확인(4.5 끝)의 결과도 V의 것을 그대로 옮겨 적는다. 이슈 글은 그대로이고 항목은 줄을 가리키지 않는다. V에서 호출 상한으로 견주지 못했으면 처음부터 검사한다.
- PR 설명 확인(4.5 끝)의 결과도 V의 것을 옮겨 적는다. PR 글도 사람의 커밋도 그대로이고 수정안의 변경은 PR의 변경으로 세지 않는다. 더한 줄을 가리킨 항목은 패치로 줄 번호를 옮기고, 패치가 그 줄을 바꿨거나 V에서 호출 상한으로 견주지 못했으면 처음부터 검사한다.
- PR 단위 확인의 결과도 V의 것을 옮겨 적는다. PR 단위 확인은 파이프라인의 수정안이 데려온 커밋을 PR의 커밋으로 세지 않으므로(4.5 끝) 머지 커밋에서 다시 봐도 볼 것이 같다. 수정안이 더한 파일(만든 테스트)로 "바뀐 파일" 조건이 달라질 수 있는 것은 받아들인다. 다음 커밋의 검사가 다시 본다.
- 모델 판단으로 찾은 위반을 고친 수정안도 옮겨 적는다. 그 위반은 고친 뒤 도구로 재검사하지 못한 것이고(4.8의 5번) 수정안 PR에 그렇게 적혔으며 사람이 보고 머지했다. 결과 코멘트에 "수정안이 고친 위반 중 N건은 모델 판단으로 찾은 것이라 도구로 재검사하지 못했고, 그 줄이 바뀐 것까지만 확인했습니다"를 같이 적는다. 머지 커밋에서 모델 판단을 다시 돌리지는 않는다.
- 검사 기록: V의 끝난 검사가 모두 지금 파이프라인 코드의 것이고, 이 커밋에 끝난 검사(`done`, `error`)가 아직 없다. 동기화가 배포 뒤 다시 넣은 작업(`new_pipeline`)은 그래서 처음부터 검사한다. 옮겨 적기만 하면 옛 코드의 결과가 새 코드의 기록으로 남는다.
- 남은 위반을 옮길 수 있다: 수정안이 고친 위반(기계적 수정은 고친 뒤 없어진 것, 모델 수정은 대상)을 빼고, 남은 위반(고치지 않기로 한 것 등)은 패치로 줄 번호를 옮긴다. 패치가 그 줄을 바꿨거나, 옮긴 줄의 내용이 위반의 줄 내용과 다르거나, 그 뒤 같은 줄을 고친 수정안이 거절됐으면 처음부터 검사한다.
- `/recheck`가 아니다. `/recheck`는 늘 처음부터 검사한다.

하나라도 맞지 않으면 지금처럼 처음부터 검사한다(까닭은 워커 로그에 남는다). 옮겨 적은 결과 코멘트는 테스트 줄 아래에 "이 커밋은 수정안 #N을 머지한 커밋이고, 내용이 검증한 수정안과 같아 다시 검사하지 않았습니다. 결과는 커밋 V의 검사와 수정안 #N의 검증에서 옮겨 적었습니다"를 적는다. 테스트 결과는 V의 것이고, 출구 검사가 고친 뒤 같은 결과를 확인했다. 바뀐 줄 커버리지는 V의 diff로 잰 값이라 옮기지 않는다. 이 커밋에는 보통의 검사와 같은 `done` run(`pipeline_commit` 포함), 위반 기록, 체크포인트가 남는다. 머지된 수정안의 스레드 해결(4.11 `resolve`)은 따로 된 작업이라 그대로 일어난다.

**명령 (v1 F11)**

- `/recheck`: PR의 지금 head로 다시 검사한다. 캐시는 그대로 쓰므로 입력이 같으면 결과가 같다.
- `/fix`: 이 커밋에서 수정안을 내지 못하고 끝난 수정(검증 실패)과 호출 상한에 걸려 처리하지 못한 위반 판단·수정을 다시 돌린다. PR 호출 상한을 한 번 더 받는다(저장소의 하루 상한 안에서). 시도 세대를 올려 수정 작성의 저장된 결과를 쓰지 않는다. `require_approval: true`면 멈춰 있는 수정을 승인한다. `/fix mechanical`, `/fix model`로 묶음을 고를 수 있다. v1의 `/fix lint`는 3단계에 지원하지 않는 명령이 되었다(그 경로가 `mechanical`이 되었다). 수정안 PR이 열렸거나 닫혔거나 머지됐으면 그 번호로 답한다.
- 처리한 코멘트 ID를 저장한다. 닫힌 PR의 명령은 처리하지 않는다.
