# 문제 해결 일지

구현 중에 만난 문제와 해결 과정. 각 항목은 상황, 원인, 해결, 확인 방법 순서로 적는다.

## 2026-11-17 · 사용자가 파이프라인 코멘트를 지우면 그 PR의 작업이 전부 멈출 뻔함 (1단계)

**상황.** 파이프라인은 PR당 코멘트 하나를 달고, 다음 커밋부터는 SQLite `runs`에 저장한 코멘트 ID로 같은 코멘트를 고친다 (DESIGN.md F9). 기능 요구사항에는 "사용자가 그 코멘트를 지우는 경우"가 없었다.

**원인.** 코멘트가 지워지면 저장된 ID로 보내는 수정 요청(`PATCH /issues/comments/{id}`)이 404를 돌려준다. gh 호출 실패는 환경 오류로 다뤄지므로 작업은 재시도 3회 뒤 실패하고, 다음 커밋의 작업도 `runs`에서 같은 지워진 ID를 꺼내 똑같이 실패한다. 결과적으로 그 PR에는 다시는 결과가 달리지 않는다. 작업 범위 판단 기준의 "작업이 멈춤"에 해당한다.

**해결.** `worker/github.py`의 `upsert_comment`에서 수정 요청이 404면 저장된 ID를 버리고, 파이프라인 표시(`<!-- pr-proof -->`)와 작성자로 코멘트를 다시 찾고, 없으면 새로 단다. 404가 아닌 실패(인증 만료 등)는 그대로 올려 환경 오류로 처리한다.

**확인.** `tests/worker/test_github.py`
- `test_deleted_comment_falls_back_to_create`: 수정 404 → 다시 찾기 → 새로 달기 순서로 호출됨
- `test_other_patch_errors_propagate`: 401은 숨기지 않고 올라감
- `test_finds_own_marked_comment`: 다른 사람이 표시를 흉내 낸 코멘트는 건너뜀

**배운 점.** 파이프라인이 GitHub에 남긴 것은 사람이 언제든 지우거나 바꿀 수 있다. 저장해 둔 외부 리소스 ID는 "없을 수 있음"을 정상 경로로 다뤄야 한다.

## 2026-11-18 v2 1단계: 실제 PR 확인과 모델 비교 (haiku, sonnet)

**상황.** v2 1단계(규칙 읽기, 검사기 작성, 위반 찾기, 코멘트)를 `v2/stage1`에 만든 뒤 실제 모델과 실제 PR로 확인했다.

**실제 PR.** `Eunryong/eval` PR #12에 `orders/services/notify.py`의 `print`를 넣었다. 웹훅으로 들어온 작업이 "문서 규칙" 절을 달았고 그 줄이 출처(`README.md > 코드 규칙 > 출력`)와 검사기 본문과 함께 나왔다. 첫 커밋은 모델 호출 14회, 226초였다. 같은 PR의 두 번째 커밋은 모델 호출 0회, 16초였고 새 `print` 줄이 하나 더 잡혔다.

**모델 비교.** eval의 README(`main` 2070aa1)로 규칙 읽기와 검사기 작성을 한 모델로만 돌렸다. 가벼운 모델과 무거운 모델 자리에 같은 모델을 넣었고, 실행은 모델마다 한 번이다. 채점은 정해 둔 위반 파일 둘(위반 개념 8개, 잡히면 안 되는 줄 6개)로 했다. 스크립트는 저장소에 넣지 않았다.

| | haiku (`claude-haiku-5-5`) | sonnet (`claude-sonnet-5-5`) |
| --- | --- | --- |
| 읽은 규칙 | 10 | 8 |
| 원문 확인에서 버린 규칙 | 0 | 0 |
| 검사기를 얻은 규칙 | 9 | 8 |
| 모델 호출 | 13 | 12 |
| 규칙당 평균 회차 | 1.2 | 1.38 |
| 토큰 (입력 / 출력) | 66,317 / 40,843 | 52,601 / 12,247 |
| CLI가 알려 준 정가 추정 | $0.023 | $0.203 |
| 걸린 시간 | 211초 | 116초 |
| 잡은 위반 개념 | 8 / 8 | 8 / 8 |
| 잘못 잡은 줄 | 0 | 0 |

- 규칙 수가 다른 이유: haiku는 "구조" 절의 "반대 방향 import는 금지한다"를 규칙으로 하나 더 뽑았고, "함수는 모듈 수준 변수를 바꾸지 않는다. `global` 문을 쓰지 않는다."를 둘로 나눴다.
- haiku는 이 실행에서 `print` 규칙의 인용을 첫 문장만 옮겼다. PR #12의 실행에서는 두 문장을 옮겼다. 같은 문서에서 인용의 범위가 실행마다 달라질 수 있고, 그러면 규칙 id도 달라진다. 캐시가 있는 동안에는 한 번 읽은 결과가 유지된다.
- 범위 추정: sonnet은 범위가 없는 규칙 셋(매직 값, `global`, 금액)에서 `tests/**`를 뺐다. haiku는 하나도 빼지 않았다.
- 테스트 파일 이름 규칙: haiku는 3회 안에 검사기를 얻지 못했다. sonnet은 2회차에 얻었고 PR #12의 실행(haiku 두 번 뒤 sonnet)에서도 얻었다. 다만 이 규칙은 파일 이름에 대한 것이라 코드 예시로 확인한 검사기가 뜻대로 도는지는 재지 못했다(경로 패턴 검사기는 1단계 직후).
- 두 모델이 모두 실패한 규칙이 없어 opus는 돌리지 않았다.

**읽는 법.** 표본이 README 하나, 실행 한 번이라 두 모델의 우열을 말하기에는 부족하다. 이 저장소의 규칙에서는 가벼운 모델만으로 검사기가 대부분 1회차에 채택된다는 것, 차이는 규칙을 나누는 방식과 범위 추정에서 났다는 것까지가 관찰이다. 비용은 구독 로그인에서 CLI가 정가로 추정한 값이고 청구액이 아니다.
