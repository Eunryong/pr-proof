# 문제 해결 일지

구현 중에 만난 문제와 해결 과정. 각 항목은 상황, 원인, 해결, 확인 방법 순서로 적는다.

## 2026-11-17 · 사용자가 파이프라인 코멘트를 지우면 그 PR의 작업이 전부 멈출 뻔함 (1단계)

**상황.** 파이프라인은 PR당 코멘트 하나를 달고, 다음 커밋부터는 SQLite `runs`에 저장한 코멘트 ID로 같은 코멘트를 고친다 (DESIGN.md F9). 기능 요구사항에는 "사용자가 그 코멘트를 지우는 경우"가 없었다.

**원인.** 코멘트가 지워지면 저장된 ID로 보내는 수정 요청(`PATCH /issues/comments/{id}`)이 404를 돌려준다. gh 호출 실패는 환경 오류로 다뤄지므로 작업은 재시도 3회 뒤 실패하고, 다음 커밋의 작업도 `runs`에서 같은 지워진 ID를 꺼내 똑같이 실패한다. 결과적으로 그 PR에는 다시는 결과가 달리지 않는다. 작업 범위 판단 기준의 "작업이 멈춤"에 해당한다.

**해결.** `worker/github.py`의 `upsert_comment`에서 수정 요청이 404면 저장된 ID를 버리고, 파이프라인 표시(`<!-- pr-proof -->`)와 작성자로 코멘트를 다시 찾고, 없으면 새로 단다. 404가 아닌 실패(인증 만료 등)는 그대로 올려 환경 오류로 처리한다.

**확인.** `tests/worker/test_github.py`
- `test_deleted_comment_falls_back_to_create`: 수정 404 → 다시 찾기 → 새로 달기 순서로 호출됨
- `test_other_patch_errors_propagate`: 401은 숨기지 않고 올라감
- `test_finds_own_marked_comment`: 다른 사람이 표시를 흉내 낸 코멘트는 건너뜀

**배운 점.** 파이프라인이 GitHub에 남긴 것은 사람이 언제든 지우거나 바꿀 수 있다. 저장해 둔 외부 리소스 ID는 "없을 수 있음"을 정상 경로로 다뤄야 한다.

## 2026-11-19 확인 대상(code·pr·human) 고르기 (완료 기준 1a-4)

**왜.** MathLLM README에는 코드 규칙, PR 규칙(브랜치, 커밋 메시지), 사람의 절차(데이터 누수 확인, PR 체크리스트)가 한 문서에 섞여 있다. 절을 설정으로 지정하게 하지 않고, 규칙 읽기에서 모델이 규칙마다 무엇을 보고 확인하는 규칙인지 고르게 했다. `code`만 검사하고 `pr`과 `human`은 코멘트에 목록으로만 보인다.

**방법.** MathLLM `origin/main`(57edb48)의 README와 eval의 README를 실제 모델로 읽었다. MathLLM은 sonnet 3번, haiku 3번, eval은 한 번씩. 규칙 읽기만 돌렸고 PR이나 코멘트는 만들지 않았다.

- 코드 규칙 7개(README의 "코드 규칙" 1~7번)는 6번 모두 `code`였다. 파일 이름 규칙(`build_<대상>.py`)도 `code`다.

## 2026-11-19 경로 패턴 검사기와 범위 추정의 효과 확인 (완료 기준 1a-1 ~ 1a-3)

**왜.** 파일 이름 규칙("테스트 파일 이름은 `test_<모듈>.py`다")은 코드 예시로 가릴 수 없어 검사하지 못하거나 뜻이 어긋난 검사기로 남았다. 범위 추정은 glob의 모양만 보고 받아서 `**/test_*.py` 같은 좁히는 glob을 버렸다.

**경로 패턴 검사기.** 규칙 읽기가 경로 규칙에 힌트(`check: path`)를 달고, 그 규칙은 선언(JSON: `applies_to`, `condition`, `pattern`)과 경로 예시로 검사기를 얻는다. 선언은 파이프라인의 고정 스크립트가 샌드박스에서 경로에 맞춘다. PR이 새로 만든 파일만 보고 위반은 파일 단위다.

- 실제 모델 확인: eval `main`(2070aa1) 위에 `tests/pricing_test.py`와 `tests/test_fee.py`를 더한 로컬 커밋(push하지 않음)으로 규칙 읽기 → 검사기 작성 → 위반 찾기를 haiku로 돌렸다. 테스트 파일 이름 규칙(`R-readme-4be42e5f`)이 1회차에 `path-pattern` 검사기 `08902946`을 얻었고, `tests/pricing_test.py`만 "(파일 이름·경로)" 위반으로 나왔다. `tests/test_fee.py`는 나오지 않았다.
- 모델이 쓴 선언: `applies_to: ^tests/(?!.*(__init__|conftest)\.py$)`, `must_match`, `pattern: (^|/)test_[^/]+\.py$`.
- 끝없이 되짚는 정규식(`^(a+)+$`)은 샌드박스의 시간 제한에서 멈춘다 (`pytest -m docker`).
- 기존 검사기의 캐시 키는 그대로다(경로 패턴의 프롬프트 버전을 따로 센다). 규칙 읽기는 프롬프트가 바뀌어 저장소마다 한 번 다시 읽는다.

**효과 확인.** base 파일 목록에 glob을 맞춰, 규칙이 적용되는 파일의 50% 이상을 빼는 glob을 버리고 코멘트에 보인다. Python 파일 4개 중 1개를 빼는 `**/test_*.py`는 받고, 4개를 모두 빼는 `**/*.py`는 버린다 (단위 테스트와 흐름 테스트).

- 모델이 적은 `unfit`은 모두 "그 이름이 모듈 수준인지 지역인지 스코프를 따져야 한다"였다. Python AST 검사기는 함수의 지역 이름·매개변수·`global` 선언을 따로 세고, 모듈 수준 이름의 메서드 호출·항목 대입·`del`을 잡았다. PR에서는 10번 줄만 잡고 모듈 수준의 `_seen_orders = []`(9번 줄)는 잡지 않았다.
- 다른 규칙에서도 `unfit`이 나왔다: 의존 방향 import 규칙(상대 import는 파일 경로를 알아야 한다)과 print 규칙(별칭 호출). 그 규칙들도 2회차의 Python AST로 채택됐다. 검사기 작성 호출이 끝까지 돌린 회에서 12–14회로, 위 절의 10회보다 늘었다.

**2. 규칙 읽기의 수정 방법 힌트 (4.4).** 프롬프트가 "어긴 코드를 동작을 바꾸지 않고 그 자리에서 고칠 수 있으면 `model`"이라고 물었다. 이 규칙은 고치면 부수 효과가 없어지므로 그 물음에 `none`이 맞는 답이 된다. 4.4는 `none`을 "이름 변경처럼 영향 범위가 넓은 것"으로만 정했고, 동작이 바뀌는 수정은 4.6의 안전망과 4.8의 테스트, 사람의 머지가 맡는다. 그래서 첫 잘못은 프롬프트의 문장이다. 저장된 규칙 읽기(같은 프롬프트, eval README) 6번 중 5번이 그 규칙(나뉜 경우 두 규칙 모두)을 `none`으로 답했다(sonnet 4/5, haiku 1/1). "고치면 동작이 달라질 수 있다는 것만으로 `none`을 고르지 않는다, 다른 파일의 사용처까지 바꿔야 하면 `none`"으로 바꾸고 같은 저장소에서 규칙 읽기만 돌렸다.

| 프롬프트 | 그 규칙의 fix | 다른 규칙 |
| --- | --- | --- |
| 고치기 전 (3회) | `none` 3/3 (2번은 문장을 둘로 나눔) | import 규칙 둘 3/3 `none`, print 1/3 `none` |
| 고친 뒤 (3회) | `model` 3/3 (3번 모두 한 문장) | import·print·금액·데이터 클래스 `model`, 테스트 파일 이름(경로)은 `none` |

**3. 끝까지 (전체 README, 가짜 GitHub, 푸시 없음).** `fix_e2e.py`를 그대로 썼다.

| 회 | 01 (`> 50`, 15번 줄) | 02 (`_seen_orders.append`, 10번 줄) | 호출 (규칙·검사기·판단·수정) |
| --- | --- | --- | --- |
| 1 | 잡힘(ast-grep), fix → 수정안 PR #900, 검증 통과 | 잡힘(python-ast), 규칙의 fix `model`, 모델이 `skip`: "없앨지, 인자나 객체 상태로 바꿀지 사람이 정해야 하고 … 동작에 영향" | 1·12·1·1 |
| 2 | 같음 | 규칙 읽기가 문장을 둘로 나눔. "함수는 모듈 수준 변수를 바꾸지 않는다."로 잡힘(python-ast), fix `model`, 모델이 `skip`: "어디서 쓰이는지 알 수 없어 … 사람이 방법을 골라야" | 1·14·1·1 |
| 3 | 같음 | 잡힘(python-ast), fix `model`, 모델이 `skip`: "기록이 필요한지, 어디에 둘지 사람이 정해야" | 1·12·1·1 |

세 회 모두 검사하지 못한 규칙이 없었다. 수정안 PR은 세 회 모두 01 한 건만 고쳤다.

**4. 수정 판단 (세 번째 시도, 되돌림).** 수정 판단 프롬프트도 fix를 "동작이 바뀌지 않을 것이 분명하다", skip을 "동작이 바뀔 수 있거나"로 정해 2와 같은 전제가 있었다. "규칙이 막는 일을 그만두게 해 동작이 그만큼 달라지는 것은 괜찮다, 호출하는 쪽이 받는 결과가 바뀌면 skip"으로 바꾸고 1회의 위반 둘로 판단만 다시 물었다. 고친 프롬프트 3/3, 고치기 전 프롬프트 3/3 모두 02를 `skip`했다. 이유가 "동작이 바뀔 수 있다"에서 "다른 코드가 그 목록을 읽을 수 있다, 제거·반환·인자로 넘기기 중 사람이 골라야 한다"로 옮겨 갔을 뿐이다. 효과가 없어 되돌렸다(바꾸면 모든 저장소가 판단을 다시 묻는다). 고치는 방법이 여럿이라 사람이 고르게 두는 것은 4.6이 모델에 맡긴 판단이고 설계대로다. 파이프라인 쪽 시도 세 번을 여기서 다 썼다.

그래서 **2-1은 아직 채우지 못했다.** 남은 선택지는 저장소 주인이 정한다(BACKLOG의 2-1 항목): README의 그 규칙에 고치는 방법을 적기(지키는 예. 수정 판단은 규칙 원문을 읽는다), 수정 판단의 입력에 그 이름의 쓰임을 넣는 항목(6단계)을 앞당기기, 2-1의 기준을 다시 보기. 1의 순서 변경은 11.1에 적었고 되돌릴 수 있다.

**결과 파일.** `scratchpad/s2c/m/unfit-{full,split}-N/result.json`(검사기 본문, 예시, 회차, PR에서 잡은 줄), `scratchpad/s2c/m/{fixhint,oldhint}-read-N/rules.json`(규칙과 수정 방법), `scratchpad/s2c/e2e-N/`(코멘트 `comment.md`, 수정 diff `fix.diff`, 수정안 PR 본문 `fix-pr-body.md`, 호출 기록 `report.json`), `scratchpad/s2c/decide/{new,old}-N.json`. 스크립트는 같은 폴더의 `measure_checkers.py`, `read_fix.py`, `fix_e2e.py`, `decide_only.py`다.

**대가.** 검사기 작성 프롬프트(ast-grep 스키마의 `unfit`, 공통 지시 한 줄)가 바뀌어 저장소마다 내용을 보는 검사기를 한 번 다시 쓴다. 경로 패턴 검사기는 프롬프트 버전이 그대로라 다시 쓰지 않는다. 규칙 읽기 프롬프트가 바뀌어 저장소마다 규칙을 한 번 다시 읽는다. 다시 읽은 규칙의 원문이 달라지면(문장을 나누는 방식) 그 규칙의 검사기도 새로 쓴다. 수정 방법이 `model`인 규칙이 늘어 수정 판단의 모델 호출이 늘 수 있다.
